# Composio client SDK feedback from the replay prototype

These findings come from implementing and testing the complete session and file workflow against `@composio/client@2.0.0-rc.7`, including live Google Drive execution.

| Friction | Why it matters for replay | Suggested SDK change |
| --- | --- | --- |
| File calls take a mount ID first and put `session_id` in the parameter object, while other session calls take the session ID first. | A session recorder needs special method-specific argument extraction even though every operation belongs to the same session. | Add session-bound file helpers such as `session.files(sessionId).list(...)`, or consistently accept the session ID as the first argument. |
| Upload and download URL methods issue a ticket but do not transfer bytes. | The meaningful file operation spans an SDK call plus a raw `fetch`, so retries, telemetry, redaction, and failure certainty must be implemented twice. | Provide `upload` and `download` helpers that perform the transfer and expose hooks for progress and telemetry while retaining the URL methods for advanced use. |
| Success has several shapes: SDK rejection, `response.error`, `data.successful`, proxy HTTP `status`, and tool-specific payloads. | A resolved SDK promise can still represent a tool or provider failure, which makes naive recording report false success. | Return one discriminated result type with a normalized success flag, failure layer, provider status, raw payload, and typed tool data. |
| Tool output under `data` is generic, including the Google Drive file ID needed by the next step. | Replay bindings cannot be type-checked across steps and must validate provider envelopes manually at runtime. | Generate result schemas per tool slug and offer a typed `executeTool<Slug>()` overload. |
| `session.link` can return a new pending account ID even when `session.toolkits` has selected a different active account, and readiness remains a separate check. | Treating the link response as the executable account either fails a healthy session or races ahead of OAuth completion. | Add an explicit `ensureConnected` or `waitForConnection` helper that resolves to the account actually selected by the session. |
| `session.proxyExecute` Drive endpoints are relative to the toolkit base URL; passing the provider path prefix produced `/drive/v3/drive/v3/...`. | A path that looks correct in isolation reaches a provider 404, and a permissive mock misses it. | Expose the resolved toolkit base URL or validate duplicated API prefixes before dispatch. |
| `session.execute` accepts an `account` field in the client type, but single-account projects reject it at runtime with code 4300. | Passing the ID resolved during connection setup breaks an otherwise healthy single-account session. | Make account selection capability-aware in the type or ignore the field when multi-account routing is disabled. |
| `RequestOptions.idempotencyKey` is accepted for compatibility, but the declaration says the API sends no idempotency header. | A timed-out write has an unknown outcome, so safely retrying session creation, execution, upload, or deletion is impossible. This driver disables automatic write retries as a result. | Implement real idempotency keys for mutating endpoints and document their deduplication window and scope. |
| Session deletion and mount-file deletion are separate operations, and deleting a mount prefix does not recursively remove its files. | A recorder must list every owned file, delete each path, list again to verify it is empty, delete the session, then retrieve it to verify the 404. | Offer a scoped recursive cleanup operation with a typed receipt listing deleted resources and any partial failures. |
| Proxy media responses vary by content: the live CSV response returned inline text under `data`, while binary responses can return a transient `binary_data.url`. | Callers need content-type-specific branching and sometimes leave the SDK for another signed-URL transfer. | Return a discriminated inline-versus-binary response and add a helper that always yields bytes or a stream. |

The largest product issue is idempotency. Session replay needs to distinguish a confirmed failure from an unknown write outcome; without server-backed idempotency, automatic recovery can duplicate provider side effects.
